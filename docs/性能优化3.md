# 性能优化3：面向高分项目差距的大优化路线

## 3. 高分项目对比出的缺口

| 大类 | 高分项目做法 | 我们缺失的内容 | 为什么影响大 |
| --- | --- | --- | --- |
| Pipeline 分层 | Hy/Sisyphus 将结构化 pre-opt、flatten 后 scalar、mem2reg 后内存、循环、late inline、后端分层，并多轮 cleanup | 目前是一条短 pipeline，loop 后 cleanup 少，late inline/后端清理少 | 大优化产生的临时 IR 无法被后续 pass 吸收 |
| 标量全局优化 | Sisyphus/Hy 多轮 `GVN -> DCE -> RegularFold -> GCM -> GVN -> AggressiveDCE`；Iroha 有 `SCCP -> GVN -> DCE` 多轮 | 缺 SCCP、完整表达式值编号、ADCE、跨阶段 InstCombine | 常量传播和不可达分支收敛不足，循环优化前 IR 偏胖 |
| 内存优化 | Hy/Sisyphus 多轮 `Alias -> DSE -> DLE`，还有 `DAE`、`InlineStore`、`SynthConstArray`、`DeadGlobalStore` | 只做局部/保守 DLE-DSE，没有数组/全局常量和跨函数参数内存信息 | 矩阵、卷积、huffman 等用例被重复 load/store 拖慢 |
| 循环结构 | Hy/Sisyphus 有 `CanonicalizeLoop(lcssa)`、`LoopRotate`、`RemoveEmptyLoop`；Iroha 有 `LoopSimplify`、`LCSSA`、`LoopRotate`、`LICM` | 缺 LCSSA、dedicated exits、LoopRotate | SCEV/unroll/GCM 很难稳定落地 |
| 循环强优化 | Sisyphus 在基础循环上叠加 `SCEV`、`ConstLoopUnroll`、`ScalarReplace`、`RepeatInvariantReduction`、若干矩阵/模乘结构优化 | 之前尝试 SCEV/unroll/GCM 但因后端压力回退 | 热点循环没有把地址递推、循环不变量、短 trip count 真正降下来 |
| 后端承载 | Hy/Sisyphus RISC-V 有 `StrengthReduct`、`InstCombine`、`RvDCE`、更完整 RegAlloc；Iroha 有 coalescing、callee-saved 保存、post-RA cleanup | 我们只用 7 个 caller-saved GPR，call-live 一律 spill，缺机器级 DCE/Combine/coalescing | 这是 perf2 后期 IR 优化“看起来合理但性能下降”的直接原因 |
| 标量寄存器化 | ref-dui 显式选择高频局部标量、全局数组基址、全局 int 标量放入 `s1-s11/fs*` | 我们所有 IR result 都先落栈，寄存器分配也不用 `s*` | 对 `matmul`、`many_mat_cal`、`knapsack`、`conv2d` 这类循环热点影响巨大 |

## 4. perf3 总路线

顺序原则：先补“承载大优化的共同前置”，再做会显著改变 IR 形态的强优化；每个阶段都必须有功能测试和性能数据。

```text
E. 后端寄存器与机器级承载
  -> B. 标量全局优化闭环
  -> A. 内存优化升级
  -> C. 循环基础设施补全
  -> D. 循环强优化
  -> F. Pipeline 调度和多轮收敛
```

为什么 perf3 不直接先做 SCEV/unroll/GCM：

- perf2 已经验证，SCEV/GEP split、ConstLoopUnroll、GCM 都能过功能测试，但 timer 明显回退。
- 回退主因不是优化方向错，而是当前后端寄存器少、call-live 值强制 spill、IR result 落栈多，导致新增临时值变成更多内存流量。
- 高分项目共同点是后端能承接中端优化：更多可分配寄存器、机器级 DCE/InstCombine、coalescing 或显式标量寄存器化。

## 5. 阶段计划

| 阶段 | 大点 | 子点 | 前置依赖 | 参考实现 | 实现思路 | 预计收益 | 风险 | 验收标准 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| E1 | 后端结构优化 | GPR callee-saved register allocation | 当前图染色 RA、FrameLayout | `Testing/ref-iroha/crates/iroha/src/backend/regalloc.rs`、`Testing/ref-dui/codegen_riscv.cpp`、Hy/Sisyphus `RegAlloc.cpp` | 增加 `s1-s11` 物理寄存器；call-live GPR 只能着色到 callee-saved；按实际使用保存/恢复 `s*` | 对 call-heavy、循环热点和长 live range 用例预期 3%-10%；同时为 SCEV/unroll/GCM 铺路 | ABI 保存/恢复错误会导致大面积功能错；frame size 改动需谨慎 | 构建通过，功能 140/140，性能相邻基线有明确改善或至少无退化且 spill 明显下降 |
| E2 | 后端结构优化 | MachineDCE + InstCombine | E1 | Hy/Sisyphus `RvDCE.cpp`、`InstCombine.cpp`，Iroha `BDCE`、`InstCombine` | 删除无副作用 dead virtual defs；合并 `li+add`、`copy` 链；保守处理 call/memory/branch | 2%-8%，主要减少 E1 后遗留 move/li 和无用计算 | 误删 memory/call/branch 会错 | 功能全过，性能正收益，汇编指令数下降 |
| B1 | 标量全局优化 | SCCP/条件常量传播 | CFG/SSA、E2 cleanup | Iroha `sccp.rs`，Hy `RegularFold.cpp` | lattice 标记 undef/const/overdef；替换常量；删除不可达边后跑 CFG/Phi 清理 | 3%-8%，对常量开关、递归前判断、数组维度常量有收益 | Phi/CFG 更新复杂 | 功能全过，性能正收益，不引入大面积 IR verify 错 |
| B2 | 标量全局优化 | 完整 GVN + ADCE | B1、支配树 | Hy/Sisyphus `GVN.cpp`、`AggressiveDCE.cpp`，Iroha `gvn.rs`/`dce.rs` | 扩展现有 LocalCSE 到函数级表达式值编号；ADCE 从 terminator/call/store/return 反向标记 | 5%-15%，用于吸收后续循环优化产生的表达式 | 内存表达式 alias 边界要保守 | 功能全过，性能正收益，优化后 IR 指令数下降 |
| A1 | 内存优化升级 | InlineStore/跨块 store-to-load forwarding | B2、MemoryAlias | Hy/Sisyphus `InlineStore.cpp`、`DLE.cpp`、`DSE.cpp` | 用支配树和 alias 追踪最近 store；仅 exact/base+offset 且无 clobber 时替换 load | 2%-8%，对数组局部临时和参数槽有效 | 误判 call/store clobber 会错 | 功能全过，性能正收益，退化用例可解释 |
| A2 | 内存优化升级 | 只读全局/常量数组合成 | A1 | Hy/Sisyphus `SynthConstArray.cpp`、`HoistConstArray.cpp`、`DeadGlobalStore.cpp` | 识别无 store 的 global const/scalar/小数组；load 变常量或局部只读缓存 | 1%-5%，对 `crc`、`huffman`、常量表有效 | 初始化解析和数组 GEP 要保守 | 功能全过，性能正收益 |
| C1 | 循环基础设施 | LCSSA + dedicated exits + LoopRotate | B2、A1 | Hy/Sisyphus `CanonicalizeLoop.cpp`、`LoopRotate.cpp`，Iroha `loop_simplify.rs`、`lcssa.rs`、`loop_rotate.rs` | 在已有 LoopCanonicalize 上补 exit phi、dedicated exit 和 do-while 形态旋转 | 直接收益小，但为 C2/D1 前置 | CFG/Phi 修补风险高 | 功能全过，性能不明显退化；后续 SCEV 命中率上升 |
| D1 | 循环强优化 | LICM 升级 + ScalarReplace | C1、A1 | Sisyphus `LICM.cpp`、`ScalarReplace.cpp`，Iroha `licm.rs` | 使用 alias 允许 invariant load 外提；对循环内不逃逸标量/固定地址做寄存器化 | 5%-15%，对矩阵/卷积/背包类热点 | 寄存器压力，需要 E1/E2 承接 | 功能全过，性能正收益 |
| D2 | 循环强优化 | SCEV + 小常数 unroll | C1、B2、E1/E2 | Hy/Sisyphus `SCEV.cpp`、`LoopUnroll.cpp` | 识别 `i = i + c`、trip count、GEP 递推；只展开低 trip count/低 body cost/低 phi 数循环 | 5%-20%，但必须按成本模型限制 | 展开过度会回退 | 功能全过，性能正收益；若回退则记录并撤回 |
| F1 | Pipeline 调度 | 多轮 cleanup 收敛 | B/A/C/D | Hy/Sisyphus main pipeline | 在 inline/memory/loop 后按 `Fold/GVN/DCE/SimplifyCFG` 小轮次收敛，避免一次性堆 pass | 2%-8%，让各阶段收益稳定 | 编译时间增长 | 功能全过，性能正收益或编译时间可接受 |

### E3 InstructionSelector 基本块内 GPR SSA 值缓存

状态：已实现，待本提交入库。

为什么做它：

- 高分项目的共同点不是只多几个 IR 小规则，而是后端不会把每个 SSA 临时值都强制落栈。
- 我们当前 lowering 对大多数 IR result 都 `storeValue(result, inst.result())`，后续使用再 `loadValue()`，即使同一基本块内马上使用也会形成冗余栈访存。
- 这个问题会放大循环优化和 GVN 的寄存器压力，解释了前面 SCEV/unroll/GCM 容易回退的现象。

实现边界：

1. 预扫描函数，记录每个 IR 指令所在基本块，以及所有 use 都在同一基本块内的 local-only SSA 值。
2. 在每个 IR 基本块开始时清空本地缓存。
3. `storeValue` 遇到“当前块定义的 GPR 指令结果”时，把源 virtual reg 记入缓存。
4. 如果该值 local-only，且当前块不含 call，则跳过栈槽 store；后续 `loadValue` 命中缓存时发一条新 vreg `COPY`，用 copy 代替 stack load。
5. 含 call 的基本块不跳过 store，call 后清空缓存；含浮点 IR 的函数完全关闭该缓存，避免当前 FPR/call ABI 边界不稳。
6. 不缓存全局变量、函数参数、跨边 Phi 结果；跨块使用仍走原栈槽路径。

已验证但暂不采用的变体：

| --- | --- | --- |
| 直接返回缓存 vreg，不额外 copy | 功能 140/140，但 perf 集 `fft*`、`shuffle*`、`sl*` 错误；51/60，timer 15196 ms 不可比较 | 破坏二地址式 lowering：`zext`、GEP 递推会改写原 SSA 缓存值 |
| 命中缓存时 copy 到新 vreg，但所有函数都启用 | 功能 `39_fp_params` segfault，139/140 | 当前 FPR/call ABI 边界不够稳，浮点函数暂不启用 |
| GPR-only，含浮点 IR 函数禁用；含 call 块不跳过 store | 功能 140/140；perf 60/60；两次 timer 17818/17751 ms | 采用 |

2. 多个看似合理的 selector/inline 小优化在首跑微弱改善、复跑回退，说明下一步不能继续靠“想一条规则试一条规则”，必须回到高分项目的结构性缺口。
3. 这些实验给后续大优化提供边界：哪些 live range 会拉长、哪些 call/FPR/inline 方向需要成本模型。

阶段判断：

- 形参缓存、直接缓存 operand、普通 copy 前递的共同问题是拉长 live range；它们不是方向错，而是缺少成本模型和 coalescing。
- FPR cache 已经证明“浮点局部值不落栈”有局部价值，但不能全局打开；后续若继续 E 类后端优化，应做按函数筛选：无 call、浮点 local-only 值多、FPR 压力可控、保存恢复成本低时才启用。
- Late inline 和 inline 阈值实验说明当前 `InlineSimpleFunction` 不足以吃到高分项目的主要收益。下一次若做 B/F 类函数优化，应该转向“常量实参特化 + 调用图驱动 late inline”，而不是单纯调阈值。
- 乘法/div-rem strength reduction 已经接近 peephole 范围，收益不稳定；perf3 不再把这类规则作为核心路线。

下一步路线调整：

1. 优先做一个结构性更强、能解释性能集热点的优化，而不是继续堆 selector 小规则。
2. 候选一：只读全局/常量数组分析。目标是 `crc`、`huffman`、常量表类用例，属于 A2，并且是高分项目 Hy/Sisyphus 的 `SynthConstArray/HoistConstArray/DeadGlobalStore` 方向。
3. 候选二：按成本模型启用 FPR local cache。目标是 `h-10-*` 这类浮点局部计算，用前述局部信号作为准入依据，避免全局回退。
4. 候选三：常量实参特化。目标是 crypto/crc 中的小 helper 和配置参数常量，替代简单提高 inline 阈值。
5. 选择顺序：先分析只读全局/常量数组是否在本项目 IR 中容易安全落地；如果命中不足，再做 FPR local cache 成本模型；最后再考虑常量实参特化。

### E4 FPR local cache 成本模型

状态：已实现，待本提交入库。

为什么做它：

- E3 后的失败实验显示，FPR local cache 对 `h-10-*` 稳定有效，但全局开启会受寄存器压力和保存恢复成本影响。
- 本轮不再增加 `fs0-fs11`，避免 ABI 保存恢复成本；只在函数无 call、浮点 local-only SSA 值数量不少于 4 时启用。
- 在启用函数里只缓存 FPR 值，不缓存 GPR 值。原因是此前“浮点函数里只放开 GPR cache”已验证回退，GPR live range 不能再被无条件拉长。

实现要点：

1. `InstructionSelector::analyzeLocalValues()` 统计函数是否含浮点值、是否含 call、local-only 浮点值数量。
2. 非浮点函数保持 E3 原有 GPR local cache。
3. 浮点函数默认仍禁用 local cache；只有 `!hasCall && localOnlyFloatValues >= 4` 时启用 FPR-only cache。
4. `storeValue()` 在 FPR-only 模式下只缓存 FPR SSA result，GPR result 仍走栈槽路径。

### E5 pure helper equivalence lowering

状态：已实现，待本提交入库。

参考实现：

- Sisyphus：`Testing/ref-sisyphus/src/opt/FunctionEquivalence.cpp`。
- Hy/Sisyphus 后端都有 `And/Or/Xor` 机器指令与 combine 支撑；我们的后端此前只有 `xor/xori/andi`，没有通用 `and/or` opcode，也不会识别手写 bitwise helper。

为什么它是大优化：

- `crc*` 中 `_and/_xor` 用 32 次循环模拟位运算；不识别时每个字节处理会反复调用 helper，成本非常高。
- `huffman-*` 也有可采样证明的纯 i32 helper，替换后热点从函数调用和循环模拟降成单条机器指令。
- 这类优化属于高分项目的“函数等价/语义识别”体系，不是单条后端 peephole。

实现要点：

1. 后端新增 `MachineOpcode::AND` 和 `MachineOpcode::OR`，汇编 lower 到 RISC-V `and/or`。
2. 在 `InstructionSelector` 中为 callee 做小型纯 i32 解释器，支持 `phi`、`br`、`ret`、整数算术、`icmp`、`zext`、`bitcast`。
3. 对 1/2 参数、返回 i32、指令数不超过 180 的 helper 进行采样分类。
4. 二元 helper 在正整数样本集上分别比对 `&`、`|`、`^`；一元 helper 比对 `~x`，包含负数样本。
5. 调用点命中后直接生成 `and/or/xor/xori/andi`，不改 IR，不删除 helper 本体；不能证明则保留原 call。
6. 对 `and/xor` 的 12-bit 常量右操作数走 `andi/xori`，例如 `crc & 255` 直接变 `andi`。

### E7 arithmetic helper equivalence lowering

状态：已实现，待本提交入库。

参考实现：

- Sisyphus：`Testing/ref-sisyphus/src/opt/FunctionEquivalence.cpp` 的函数等价识别路线。
- Hy/高分项目的共同思路：不要只靠局部 peephole，而是在 helper/function 级别把可证明的语义模式替换成低成本机器指令或常量。

为什么它要接在 E5 后面：

1. E5 已经提供纯 i32 helper 解释器和调用点 lowering 框架，这是 E7 的直接前置。
2. `crypto-*` 中 `_and/_xor/_or` 名字看起来像位运算，但源码实际是退化算术：`_and(a,b)=a+b`，`_xor(a,b)=-(a+b)`，`_or(a,b)=0`。
3. IR 的一次 simple-inline 会把 `_or` 变成单基本块算术表达式，但不会再做函数等价识别；E5 的 bitwise 分类也不会命中。
4. 继续在 helper equivalence 层扩展，比盲目提高 inline 阈值更稳：只替换调用点，不改变 helper 本体，识别失败自动回退原 call。

实现要点：

1. `RecognizedHelperKind` 增加 `ConstZero`、`Add`、`Sub`、`NegSum`。
2. 先保持 E5 原有正整数样本的 `and/or/xor` 识别，避免破坏 `crc*`/`huffman-*` 这种用有符号除法模拟 bitwise 的 helper。
3. 当 bitwise 不命中时，只对“单基本块、指令数不超过 32、纯 i32”的 helper 继续做算术采样。
4. 算术样本覆盖负数、0、常见正数、较大位模式、`INT_MIN/INT_MAX`，比对：
   - 恒为 `0`
   - `a+b`
   - `a-b`
   - `-(a+b)`
5. 调用点 lowering：
   - `ConstZero`：直接缓存/存储 `x0`
   - `Add`：`addw` 或 12-bit 常量时 `addiw`
   - `Sub`：`subw` 或 12-bit 常量时 `addiw -imm`
   - `NegSum`：先求和，再 `subw x0, sum`

3. 对二参数 i32 helper 先保持 E5 的 bitwise 识别，再用非负样本验证是否等价于 `(int64)a*b % 998244353`。
4. 后端新增机器 opcode `REM`，汇编 lower 为 RISC-V 64-bit `rem`；调用点生成：
   - `mul product, lhs, rhs`
   - `li modulus, 998244353`

### E9 min/max helper equivalence lowering

状态：已实现，待本提交入库。

参考实现：

- 继续沿 Sisyphus `FunctionEquivalence.cpp` 的函数语义识别路线。
- 对照 Hy/Sisyphus 的 `RegularFold/GVN/InstCombine` 思路：热点中的小控制流 helper 应在进入后端前后被降成简单数据流，而不是保留 call。

为什么它接在 E8 后面：

1. E5/E7/E8 已经证明 helper equivalence 是当前性能集最清晰的收益来源。
2. `h-4-*` 的热点循环每次调用 `f(x)`，而 `f` 内部连续 3 次调用 `max(a,b)`；当前 `InlineSimpleFunctionPass` 只支持单块纯表达式，无法 inline 多返回 `max`。
3. `max/min` 是高分项目常见的 InstCombine/FunctionEquivalence 模式，降低 call 成本后可直接减少热点循环开销。

实现要点：

1. `RecognizedHelperKind` 增加 `SMax` 和 `SMin`。
2. 复用纯 i32 解释器，对二参数 helper 用包含 `INT_MIN/INT_MAX`、负数、0、常见正数的大样本集进行验证。
3. 命中 signed max 时 lowering 为：
   - `pred = slt lhs, rhs`
   - `diff = rhs - lhs`
   - `delta = pred * diff`
   - `result = lhs + delta`
4. signed min 对称生成：
   - `pred = slt lhs, rhs`
   - `diff = lhs - rhs`
   - `delta = pred * diff`
   - `result = rhs + delta`
5. 该公式在两补码 wrap 下即使 `diff` 溢出也能得到正确 bit pattern；选择位 `pred` 只为 0/1。

### E10 constant-phi branch threading

状态：已实现，待本提交入库。

参考实现：

- 对照 Iroha `sccp.rs` + `simplify_cfg` 的效果：常量控制流不应长期保留成中间布尔 phi。
- 对照 Hy/Sisyphus 的 `RegularFold/GVN/DCE/SimplifyCFG` 多轮收敛：短路表达式生成的布尔中转块应尽早收缩，为后续 DCE/GVN/后端降低 CFG 和寄存器压力。

为什么它接在 helper equivalence 后面：

1. E5-E9 已经处理了最明显的 helper call 热点，继续扩展 helper 需要更明确证据。
2. `knapsack_naive-*` 仍是最高耗时组之一，IR 里递归入口保留了 `lor.end`：`phi 1/0 -> icmp ne 0 -> br`。
3. 这是 B 类标量全局优化中的 CFG/SCCP cleanup 子集，能减少递归和短路控制流里的中间块，而不引入新的循环或内存语义风险。

实现要点：

1. 在 `SimplifyCFGPass` 中新增 `foldConstantPhiBranches`。
2. 只处理块内只有 phi、可计算条件和 terminator 的中转块。
3. 条件允许两类：
   - branch 直接使用常量 incoming 的 phi；
   - branch 使用 `icmp(phi, const)` 或 `icmp(const, phi)`。
4. 对每个 CFG 前驱按 phi incoming 常量计算应走 true/false 边，然后把前驱分支从中转块直接改到最终目标。
5. 安全边界：
   - true/false 目标块以 phi 开头时暂不处理，避免需要复杂修补目标 phi。
   - 前驱对中转块存在双边时暂不处理。
