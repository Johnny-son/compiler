# 性能优化3：面向高分项目差距的大优化路线

本文档接替 `性能优化.md` 和 `性能优化2.md`，用于记录 perf3 阶段的调研、路线、实现顺序和测试数据。前两轮已经证明：只补零散 IR 小规则，分数很难从约 19 拉到五六十分；SCEV、unroll、GCM 这类 IR 强优化如果缺少后端承载能力，也会被栈访存和寄存器压力抵消。因此 perf3 先按高分项目的完整优化体系拆解缺口，再按依赖顺序推进大优化。

## 3. 高分项目对比出的缺口

| 大类 | 高分项目做法 | 我们缺失的内容 | 为什么影响大 |
| --- | --- | --- | --- |
| Pipeline 分层 | Hy/Sisyphus 将结构化 pre-opt、flatten 后 scalar、mem2reg 后内存、循环、late inline、后端分层，并多轮 cleanup | 目前是一条短 pipeline，loop 后 cleanup 少，late inline/后端清理少 | 大优化产生的临时 IR 无法被后续 pass 吸收 |
| 标量全局优化 | Sisyphus/Hy 多轮 `GVN -> DCE -> RegularFold -> GCM -> GVN -> AggressiveDCE`；Iroha 有 `SCCP -> GVN -> DCE` 多轮 | 缺 SCCP、完整表达式值编号、ADCE、跨阶段 InstCombine | 常量传播和不可达分支收敛不足，循环优化前 IR 偏胖 |
| 内存优化 | Hy/Sisyphus 多轮 `Alias -> DSE -> DLE`，还有 `DAE`、`InlineStore`、`SynthConstArray`、`DeadGlobalStore` | 只做局部/保守 DLE-DSE，没有数组/全局常量和跨函数参数内存信息 | 矩阵、卷积、huffman 等用例被重复 load/store 拖慢 |
| 循环结构 | Hy/Sisyphus 有 `CanonicalizeLoop(lcssa)`、`LoopRotate`、`RemoveEmptyLoop`；Iroha 有 `LoopSimplify`、`LCSSA`、`LoopRotate`、`LICM` | 缺 LCSSA、dedicated exits、LoopRotate | SCEV/unroll/GCM 很难稳定落地 |
| 循环强优化 | Sisyphus 在基础循环上叠加 `SCEV`、`ConstLoopUnroll`、`ScalarReplace`、`RepeatInvariantReduction`、若干矩阵/模乘结构优化 | 之前尝试 SCEV/unroll/GCM 但因后端压力回退 | 热点循环没有把地址递推、循环不变量、短 trip count 真正降下来 |
| 后端承载 | Hy/Sisyphus RISC-V 有 `StrengthReduct`、`InstCombine`、`RvDCE`、更完整 RegAlloc；Iroha 有 coalescing、callee-saved 保存、post-RA cleanup | 我们只用 7 个 caller-saved GPR，call-live 一律 spill，缺机器级 DCE/Combine/coalescing | 这是 perf2 后期 IR 优化“看起来合理但性能下降”的直接原因 |
| 标量寄存器化 | ref-dui 显式选择高频局部标量、全局数组基址、全局 int 标量放入 `s1-s11/fs*` | 我们所有 IR result 都先落栈，寄存器分配也不用 `s*` | 对 `matmul`、`many_mat_cal`、`knapsack`、`conv2d` 这类循环热点影响巨大 |

## 4. perf3 总路线

顺序原则：先补“承载大优化的共同前置”，再做会显著改变 IR 形态的强优化；每个阶段都必须有功能测试和性能数据。

```text
E. 后端寄存器与机器级承载
  -> B. 标量全局优化闭环
  -> A. 内存优化升级
  -> C. 循环基础设施补全
  -> D. 循环强优化
  -> F. Pipeline 调度和多轮收敛
```

为什么 perf3 不直接先做 SCEV/unroll/GCM：

- perf2 已经验证，SCEV/GEP split、ConstLoopUnroll、GCM 都能过功能测试，但 timer 明显回退。
- 回退主因不是优化方向错，而是当前后端寄存器少、call-live 值强制 spill、IR result 落栈多，导致新增临时值变成更多内存流量。
- 高分项目共同点是后端能承接中端优化：更多可分配寄存器、机器级 DCE/InstCombine、coalescing 或显式标量寄存器化。

## 9. perf3 执行记录

### E1 GPR callee-saved register allocation

状态：已实现，待本提交入库。

实现要点：

1. 给后端增加 `s1-s11` 物理寄存器名称，不使用 `s0/fp`。
2. 图染色 GPR 可用集合扩展为 `t0-t6 + s1-s11`。
3. `CALL` 的 live-out GPR 不再一律 spill，而是限制着色到 callee-saved 集合；FPR 暂时保持保守 spill。
4. 根据最终着色实际使用到的 `s*`，在 prologue 保存，在每个 return epilogue 恢复。
5. 该阶段不做 peephole，不做语义激进变换，只补后端 ABI 和寄存器容量。

预期：这是 ref-dui/Iroha/Hy/Sisyphus 都具备而我们缺失的共同前置。若功能正确，预计能减少 call-live spill 和循环长 live range 溢出；如果当前高负载环境掩盖收益，需要至少观察相邻两次性能或统计 spill/save 数量。

实测结果：

| 项目 | 结果 |
| --- | --- |
| 构建 | `cmake --build build-docker -j` 通过 |
| 功能测试 | `compiler2026-riscv-function` ASM 140/140 |
| 性能测试 | `2026_performance` 60/60 |
| 当前相邻基线 | `perf3-baseline-current.csv`：timer 23931 ms，wall 31314 ms |
| E1 最终验证 | `perf3-e1-sreg-validated.csv`：timer 23828 ms，wall 31272 ms |
| 相对变化 | timer -103 ms（-0.43%），wall -42 ms（-0.13%） |

已验证但暂不采用的变体：

| 变体 | 结果 | 结论 |

- E1 的直接收益只有 -0.43%，低于最初对“单独阶段 3%-10%”的理想预期；原因是当前大部分热点仍由内存访存和中端未消除的重复计算主导。
- 这个阶段仍然值得合入，因为高分项目都具备 callee-saved/更大寄存器集合，而 perf2 已经看到 SCEV/unroll/GCM 在寄存器压力下回退。E1 是后续循环强优化的共同前置。
